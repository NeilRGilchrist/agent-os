# FR-0008: Declared gates — the dispatcher enforces an FR's pre-review / pre-merge gates and the deploy gate checks the evidence

## Why

Project A FR-0015 said in its Notes that the Architect reviews the legacy-ID tier map *before* the PR moves to Reviewer. Nothing in the pipeline reads Notes for gates: `wave` chains dev finalize → rev tick with no hook between them, the PR opened as draft and was un-drafted by hand, and the human merged with the review never having happened. The same shape recurs three more times in Project A's next 18 days — ADR-0001 puts a **human design-review gate** in the Definition of Done of every screen-bearing FR (FR-0006, FR-0007, FR-0009) — and will recur in every project that adopts decision rights (IDEA-0056's "design-doc gate stage"). The alternative considered and rejected was a commit hook that spawns an Architect session: it fires ~8× per FR on intermediate states, costs a full context load each time, and still cannot stop a human merge. A gate declared on the FR, enforced once at the phase boundary it names, with evidence the deploy gate can lint, catches the same failure at roughly a tenth of the cost and makes the missing review visible where the human is looking — the PR's draft state and the gate's red check — instead of in a Notes paragraph nobody executes.

## What

After this FR, an FR may declare `gates:` in frontmatter — each with an `id`, the phase it follows (`after: dev | rev`), who judges it (`reviewer: human | architect`), and a one-line `scope`. The indexer validates the shape and renders it. The dispatcher honours it: after the Developer finalizes, a human gate stops the wave with a `GATE-PENDING` line naming the exact command that satisfies it, and an Architect gate spawns a one-shot Architect gate-review session whose only writable path is the evidence file. Evidence is a tracked markdown file under `specs/_gates/` on the Developer branch, written either by `dispatch.py gate pass|block` (for humans) or by the gate session and committed by the dispatcher (FR-0006's commit ownership). The Reviewer is not runnable, and the PR is not un-drafted, while an `after: dev` gate is unsatisfied; the deploy gate fails a `merged` FR whose gates lack passing evidence and an `in-review` FR whose `after: dev` gates do; `reconcile-merged` warns when a human merged past one. A `gate.decision` metrics record makes gate throughput and turnaround measurable. FRs with no `gates:` key are untouched.

## Acceptance criteria

Each AC must be independently testable. Number them; the numbers are stable for the life of the FR.

- **AC-1:** **Frontmatter shape, validated by the indexer.** `gates:` is an optional list (default `[]`) of mappings with exactly the keys `id` (slug, `^[a-z][a-z0-9-]{1,39}$`, unique within the FR), `after` (`dev` | `rev`), `reviewer` (`human` | `architect`), and `scope` (non-empty string, one line). `python scripts/index-specs.py --validate` reports an error naming the FR and the offending gate for: a missing or unknown key, a duplicate `id`, an out-of-vocabulary `after` or `reviewer`, an empty `scope`, or a non-list value. The parsed `FR` object exposes `gates` as a tuple of records. `specs/INDEX.md` renders a `Gates` column per FR (`<id>:<after>:<reviewer>` joined by `, `, or `—`). The FR template documents the key with a one-line comment and an example. Verified with fixtures for every error class and one valid two-gate FR.

- **AC-2:** **Evidence file shape and one reader.** Gate evidence lives at `specs/_gates/<FR-ID>-<gate-id>.md` with YAML frontmatter `fr`, `gate`, `verdict` (`pass` | `changes-requested`), `by` (free text: a name or `architect`), `date` (ISO date), `round` (integer ≥ 1), `head_sha` (the implementation branch tip the verdict was given against), and a free-text body. A single helper `gate_status(fr_id, gate, ref)` in `dispatch.py` reads the evidence **as committed on `ref`** — the default is the FR's **implementation branch**, resolved through `_implementation_branch_for_fr` (`claude/dev-<FR>` if it exists, else `claude/mnt-<FR>`), the convention DEC-0009 / FR-0013 AC-11 established for the rev leg; `ref=None` falls back to the working tree, any other string reads that ref — and returns one of `missing`, `pass`, `changes-requested`, or `stale` — `stale` when `verdict: pass` but `head_sha` is not an ancestor-or-equal of that implementation branch's current tip (an evidence file from a branch that was later rewritten). The `_gates/` directory is documented in `specs/README.md`. Verified against a temporary repository for all four outcomes, in both the `dev` and the `mnt` resolution (DEC-0012 item 3).

- **AC-3:** **`dispatch.py gate` subcommand for humans.** `gate list <FR>` prints one line per declared gate with its current status. `gate pass <FR> <gate-id> --by <who> [--note <text>] --apply` and `gate block <FR> <gate-id> --by <who> --note <text> --apply` write the AC-2 evidence file into the implementation worktree (creating `specs/_gates/` if absent), with `round` taken from that role's current run context (default 1) and `head_sha` from the implementation branch tip, commit it on that branch with subject `gate(<FR>): <gate-id> <verdict> by <who>`, and push the branch when a remote exists. The implementation branch and worktree are resolved through `_implementation_branch_for_fr` (`dev`, else `mnt`; DEC-0012 item 3), so a gate declared on a maintainer-mode FR is satisfiable. They refuse with one `ERROR` line — and write nothing — when `<gate-id>` is not declared on the FR, when **neither** `claude/dev-<FR>` nor `claude/mnt-<FR>` exists (the line names both candidates), or when the resolved worktree is on another branch. `block` without `--note` is refused. Without `--apply` the commands print `WOULD-GATE <FR> <gate-id> <verdict>` and mutate nothing (repository byte-identical before and after, per FR-0006:AC-12's snapshot method). The commands never touch `main`.

- **AC-4:** **Reviewer runnability honours `after: dev` gates.** `runnable_review_frs` excludes any FR with a declared `after: dev` gate whose `gate_status` is not `pass`, and `tick --role rev` / `wave` print one `SKIP` line per excluded FR naming the gate, its status, the reviewer kind, and — for `human` — the exact `gate pass` command. `explain_not_runnable(<FR>, frs, "rev")` returns the same reason. An FR whose only gates are `after: rev` is reviewable exactly as today. Verified with a temporary repository holding a dev branch with and without evidence.

- **AC-5:** **A human gate stops the wave, and only a human satisfies it.** In `wave`, after a successful Developer finalize, for each `after: dev` gate with `reviewer: human` whose status is not `pass`, the wave prints `GATE-PENDING <FR> <gate-id> reviewer=human — <scope> — satisfy with: python scripts/dispatch.py gate pass <FR> <gate-id> --by <you> --apply`, records the FR as `gate-pending` in the synthesis (per-FR result, not a failure, not an escalation), spawns no Reviewer, and exits with status `3`. Nothing in the dispatcher writes a `pass` verdict for a `human` gate: not a timeout, not a PR approval, not a `--force`. Verified by asserting no `rev` lock, no `rev` worktree, and exit code 3.

- **AC-6:** **An Architect gate spawns a one-shot gate-review session.** For an `after: dev` gate with `reviewer: architect`, `wave` (and `tick --role gat --fr <FR>`) spawns role `gat` from the new `gate-review` command with the FR ID and gate id as arguments, on a worktree cut at the current tip of the FR's implementation branch (`_implementation_branch_for_fr`: `claude/dev-<FR>`, else `claude/mnt-<FR>`) — git refuses two worktrees on one branch, so the worktree sits on a new branch `claude/gat-<FR>` created at that same commit, which satisfies "at the current tip" without detached-HEAD machinery (DEC-0012 item 5) — with a writable footprint of exactly `specs/_gates/<FR>-<gate-id>.md` (everything else denied via the same per-worktree permission mechanism the other roles use). The command instructs the agent to read the FR, the gate's `scope`, and the dev branch, and to write the evidence file with a verdict and rationale citing IDs only. `finalize <FR> --role gat --apply` commits the staged evidence and fast-forwards it onto the same implementation branch (FR-0006:AC-1 path, subject `gate(<FR>): <gate-id> <verdict> by architect`), pushes that branch, and — when the verdict is `changes-requested` — posts the evidence body as a comment on the open PR. `round` and `head_sha` for the record come from the evidence file's own frontmatter, which the gate session wrote; the dispatcher never invents either (DEC-0012 item 5). The model for `gat` follows the `architect` entry of the model table. Verified with the harness adapter stubbed: worktree ref, permission set, commit subject, and the comment call.

- **AC-7:** **Gate verdicts route the wave.** After a `gat` finalize: `pass` → the wave proceeds to the Reviewer tick as today; `changes-requested` → the wave prints `GATE-BLOCKED <FR> <gate-id> by architect` and stops (exit 3), recording `gate-blocked` in the synthesis. Rework in response to a gate block is **not** automated by this FR (see Out of scope); the synthesis line names the evidence path as the rework input. A `stale` status (AC-2) is treated as not-pass and reported as `GATE-STALE` with the two SHAs. Verified for all three verdicts.

- **AC-8:** **The PR stays a draft while an `after: dev` gate is unsatisfied.** `finalize --role dev --ready`, and any other path that un-drafts a PR — `finalize-all`, a later `finalize` on an existing PR, and the one-shot maintainer / backfill path `finalize --role mnt|bkf --ready` (`_finalize_oneshot`; the guard is factored out of `_finalize_dev` and called from both, DEC-0012 item 4) — refuses with one `ERROR` line naming the unsatisfied gate(s) and leaves the PR draft. The generated PR body gains a `## Gates` section listing each declared gate as `- <id> (<after>, <reviewer>): <status>` and is refreshed on the existing `pr.refreshed` path so the human sees gate state on the PR itself. FRs without gates get no section. Verified with `gh` stubbed.

- **AC-9:** **The deploy gate lints evidence.** In `deploy-gate.py`: for every FR with declared gates, `status: merged` requires every gate's `gate_status(…, ref=None)` on the current tree to be `pass`, and `status: in-review` requires it for every `after: dev` gate; a miss is a failure with class `gate-evidence-missing` (or `gate-evidence-stale`) naming the FR and gate, in stages `review` and `full`. In stage `dev` the same condition is a warning. FRs with no gates add nothing to the report. The `gate.run` metrics record carries the new failure classes. Verified with fixtures for merged-with-evidence, merged-without, in-review-with-rev-gate-only, and the dev-stage warning.

- **AC-10:** **`reconcile-merged` reports a merge past a gate, and still records the fact.** When a merged PR's FR has any gate whose status on the merge commit is not `pass`, reconcile prints one `WARN` line per gate (`merged past gate <id>: status <status>`), still flips the FR to `merged` (the merge happened; the gate lint in AC-9 will fail on `main` and say why), and emits the AC-11 record with `verdict: bypassed`. Verified with a temporary repository.

- **AC-11:** **One new metrics record kind.** `metrics_log.py` gains `gate.decision` with required fields `object_ids` (the FR), `gate` (id), `after`, `reviewer`, `verdict` (`pass` | `changes-requested` | `bypassed`), `by`, `round`, and `head_sha`; it is emitted by `gate pass|block`, by `finalize --role gat`, and by AC-10. `specs/_metrics/README.md` documents it. The schema validator (FR-0002) accepts it and rejects a record missing any required field. No other kind changes.

- **AC-12:** **Orchestrator command and the gate-review command.** `template/.agent-team/commands/orchestrator.md` documents the two new wave outcomes (`GATE-PENDING`, exit 3 — hand the command to the human and stop; `GATE-BLOCKED` — hand the evidence path to the human, do not start a rework round unprompted) in the Phase 2 outcome handling. `template/.agent-team/commands/gate-review.md` exists with the AC-6 instructions and the standard role preamble, and states that the session writes nothing but the evidence file. The generated wrappers under `template/.claude/commands/` and `template/.cursor/commands/` are regenerated by the bootstrap renderer and differ from the sources only by the generated-file banner and frontmatter. Role files under `template/.agent-team/roles/` are not edited; if the Developer finds the Architect role file should mention gate review, raise a `## FINDINGS` line.

- **AC-13:** **Backward compatibility, dry-run, and existing tests.** An FR without a `gates:` key produces identical indexer output (apart from the new `—` column), identical dispatcher behaviour and output, identical PR body, and identical deploy-gate results to before this FR. `wave --dry-run` prints `WOULD-GATE` lines for gates it would evaluate and mutates nothing. The implementation-role resolution of AC-2/AC-3/AC-6 runs only for an FR that declares a gate, so a gate-free FR is unaffected by it. Every test that passed before this FR still passes **except the fifteen ids DEC-0012 item 2 enumerates**, each of which pins a closed world an AC of this FR deliberately opens — the nine `Gates`-column ids in `test_index_specs_versioning.py`, `test_index_specs_dec_tr.py` and `test_spec_query.py` (AC-1), the four `gate.decision` / `gat` ids in `test_metrics_log.py` (AC-11), the one failure-class id in `test_deploy_gate_metrics.py` (AC-9), and the `orchestrator` parametrisation of `test_headless_conduct.py::test_source_minus_the_block_equals_the_pre_fr_source_apart_from_ac8` (AC-12). Each is re-pointed, never retired, skipped or `xfail`ed, and each edit is bounded by DEC-0012 item 2. ## Out of scope

- `reviewer: docs` or any reviewer kind beyond `human` and `architect`; per-AC gates; gates on TRs or DECs.
- Re-gating automatically after every rework round. AC-2's `stale` covers the branch-rewritten case only; whether a human gate must be re-passed after a Reviewer-driven rework round is left to the gate's `scope` text and the human.
- Any GitHub-side enforcement (branch protection, required checks, CODEOWNERS). Not viable while agents and the human share one GitHub identity; revisit with separate identities.
- Changing `template/.agent-team/roles/*.md`, `handoff-protocols.md`, or `escalation-matrix.md`.
- Retro-fitting `gates:` onto existing FRs in any project. Projects add them as they adopt the field (Project A adds `design-review` to FR-0006/0007/0009 and `tier-map-review`-style gates to future KB FRs after this lands).
- IDEA-0056's full decision-rights validator (tier/authorised_by/GOAL linkage). This FR is the "design-doc gate stage" slice of it only.

## Open questions

- **Q:** Should a `human` gate be satisfiable from the PR (e.g. a comment `/gate pass <id>`) as well as the CLI?
  - **Default:** No. The CLI writes a tracked, committed artifact with a `head_sha`; a comment does not. Add a PR-comment adapter later if the CLI proves too much friction — the evidence shape does not change.
- **Q:** Should `after: rev` gates block `finalize --role rev` (posting the review) the way `after: dev` gates block the Reviewer spawn?
  - **Default:** No. An `after: rev` gate is a pre-merge gate; the only enforcement available before a human merge is the PR draft state (AC-8 keeps it draft until the gate passes) and the lint (AC-9). Posting the review is not the thing to block.
- **Q:** Should the `gat` session be allowed to *edit the FR* (e.g. append a Notes clarification) as the Project A Prompt A brief contemplated?
  - **Default:** No. One writable path. A gate review that finds the spec wrong writes `changes-requested` with the finding; the Architect revises the spec in a normal `/architect` session.
- **Q:** Model for `gat`?
  - **Default:** Same as `architect` in the model table (currently opus). Gate reviews are judgment calls; that is where the stronger model earns its cost.
