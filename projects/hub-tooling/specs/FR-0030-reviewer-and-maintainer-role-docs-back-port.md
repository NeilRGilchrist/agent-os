# FR-0030: The Reviewer and maintainer docs say what the dispatcher does

## Why

ai-hub-poc corrected its Reviewer and maintainer docs (its FR-0062 and FR-0082). The template never took the corrections. After `--upgrade`, ai-hub-poc gets the template's text back, and with it a contract no part of the factory honours.

1. **A review state nobody sets or reads.** The template's Reviewer docs still tell the Reviewer to "Use `Request changes` on the PR", to "Approve the PR", and, without a dispatcher, to "use `Approve` review state". Those instructions are at `roles/reviewer.md:47,75,81`, `commands/reviewer.md:60,65` and `handoff-protocols.md:58,62,69`.
   - Under the dispatcher, the Reviewer's account authored the PR, so GitHub refuses both review states.
   - Nothing reads a review state: the deploy gate never queries GitHub, and the rework loop reads the Reviewer's text (`_resolve_rework_verdict`).
   - The artifact definitions in `handoff-protocols.md` still say review feedback "Lives at: PR review".
2. **No account of where the verdict and the review live.** DEC-0001 settled it: the verdict of record is the final message, and the review of record is the Reviewer's own `REVIEW.md`. FR-0025 then filed the review per round under `specs/_reviews/`. The reviewer command says part of this in one long bullet. The role file says none of it.
3. **Fix locations guessed from the failure message.** In ai-hub-poc, a review named a fix location from an assertion's prose. The assertion never opened that file, and two of three cycles were spent on it. The template has no rule against this. It also has no rule that a claimed location must lie inside the FR's `owns:`.
4. **An escalation with no verdict.** The role file says "Do not approve or reject the PR until Architect responds". A dispatched Reviewer cannot obey that: its run ends, and the dispatcher posts whatever its final message says.
5. **The merge boundary is only implied.** "What you must NOT do" has no merge bullet.
6. **A maintainer that escalates a regeneration step.** An owned `.claude/commands/<name>.md` is harness-guarded and generated. The maintainer command never says so, so a maintainer treats it as a footprint escalation. Only the dispatcher's spawn-time `WARN` points at the source.

The gap analysis attributes 41 ai-hub-poc test failures to these docs: 12 class C and 4 class B in ai-hub-poc FR-0062, and 12 class C in ai-hub-poc FR-0082.

## What

After this FR, the template's reviewer and maintainer docs describe the contract the dispatcher enforces today:
- **The verdict:** a `## Approve` or `## Request changes` heading opens the Reviewer's final message, and the dispatcher posts it. The full review goes in a staged `REVIEW.md`, which `finalize` files as `specs/_reviews/<FR>-r<N>.md`. No Reviewer runs `gh pr review --approve` or `--request-changes`.
- **Fix locations:** a fix-location claim cites what the failing assertion reads and stays inside `owns:`.
- **Escalation and merging:** an escalation carries `request-changes`, and a Reviewer never merges.
- **The maintainer:** an owned generated wrapper is reported as "regeneration pending", not escalated.

The four generated wrappers follow their sources. Every other line in the four documents, and every other wrapper, is unchanged.

  - **Command, `When something needs to go back:`:** step 1 says the final message opens with `## Request changes`, which the dispatcher reads as the verdict and posts.
  - **`handoff-protocols.md`:** both `Review feedback (Reviewer → Developer)` and `Approval (Reviewer → merge gate)` are redefined.

- **AC-2:** **The role file records the verdict and the review as the dispatcher handles them.** `roles/reviewer.md` gains a `## Recording your verdict` section, after `## What you must NOT do`. It states each of the following.
  - **The verdict of record.** Under a dispatcher, it is your final assistant message, or the file passed to `finalize --role rev --verdict-file`.
    - Open it with a `## Approve` or `## Request changes` heading. Those are the only two verdicts.
    - The dispatcher reads a `Verdict: approve` / `Verdict: request-changes` first line before the first heading.
    - A message with neither is posted as a plain comment carrying no verdict.
  - **The review of record.** Write your full review to `REVIEW.md` at the worktree root, open it with the same heading, and stage it, on either verdict.
    - `finalize --role rev` files it byte for byte as `specs/_reviews/<FR>-r<N>.md` (N is the round) and removes the root file from the branch.
    - It synthesises the file from your final message only when you staged none (DEC-0001, FR-0025).
    - The next Developer round reads the newest filed round. So does the rework loop, for its verdict, when your final message names none.
  - **Rounds.** Each round is its own filed file. Never edit a file under `specs/_reviews/`. Correct an earlier round's finding in this round's `REVIEW.md`. Amending your current round before you hand off is fine.
  - **Posting.** These sentences appear verbatim: `Posting the verdict to the PR is the **dispatcher's** job.` and `Nothing gates on GitHub review *state*.`
    - The section explains the same-GitHub-account refusal (the words `same GitHub account`) and the dispatcher's fallback to a comment.
    - It says the deploy gate never queries GitHub, and closes the rationale with `not because any check consumes a review state`.
  - **`Running outside the dispatcher`:** write `REVIEW.md` the same way, heading first, and commit it. You may post it to the PR as a plain comment. The sentence `Never \`--approve\`, never \`--request-changes\`.` appears verbatim.
  - **"What you must NOT do"** gains:
    - `❌ Run \`gh pr review --approve\` or \`gh pr review --request-changes\``, pointing at this section;
    - `❌ Edit a filed review under \`specs/_reviews/\``.
  - **Two negative checks:**
    - none of the four reviewer documents calls `REVIEW.md` the verdict artifact;
    - every verdict form they show resolves, under the template's `_extract_review_verdict`, to the verdict it is shown for. A bare `**Verdict:** approve` line, which that function's first-line rule does not read, is not shown as a form to use.

## Open questions

- **Q:** Should the docs use ai-hub-poc's bold `**Verdict:** approve` line, so that its FR-0062 AC-1 and AC-3a tests pass unchanged?
  - **Default:** no. The template's `_extract_review_verdict` tier 1 matches `Verdict: approve` but not `**Verdict:** approve`. A `REVIEW.md` opening with the bold form would resolve to `comment` in `_resolve_rework_verdict`'s fallback.
    - The heading form already works for both the final message and the filed review, and the reviewer command already prescribes it.
    - ai-hub-poc retargets four tests: three AC-1 tests and the AC-3a signal test.
- **Q:** Should `REVIEW.md` be called "the authoritative verdict artifact", as ai-hub-poc's role file does?
  - **Default:** no. DEC-0001 and FR-0025 make the final message (or `--verdict-file`) the verdict of record and the filed `REVIEW.md` the review of record. The dispatcher does exactly that: it posts the final message, files the review, and reads the review's verdict only as a fallback. The docs follow the code and the DECs, so there is no disagreement to flag.
- **Q:** May the no-dispatcher branch keep "use `Approve` review state" for a human reviewer, as FR-0012 AC-8 kept it?
  - **Default:** no. `/reviewer` is an agent command. Every agent here authenticates as the account that authored the PR, so the instruction cannot be followed by anyone who reads it. A human reviewer does not need the command to approve a PR. FR-0012 AC-8, FR-0006 AC-7 and FR-0021 AC-5 are revised for it (Notes, "Cascade").
