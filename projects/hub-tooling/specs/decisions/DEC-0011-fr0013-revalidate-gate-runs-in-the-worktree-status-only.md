# DEC-0011: AC-7's revalidate gate runs execute in the worktree, both `--status-only`; the dispatcher's own observation writes nothing

## Context

FR-0013 v4 was implemented at `0bf67c8` (maintainer mode, Developer round 2) and reviewed at `7528323`/`f057c6c` (`Verdict: request-changes`, round 2 of 3). Every round-1 item is closed and pinned green. One item blocks, with one escalation attached:

- **K6 — AC-7, blocking.** `_run_deploy_gate` (`dispatch.py:2649`) runs `REPO_ROOT / "scripts" / "deploy-gate.py"` with `cwd=REPO_ROOT` — the primary checkout — and `deploy-gate.py` resolves its own `REPO_ROOT`, `SPECS_DIR` and `TESTS_DIR` from `__file__`. So both the pre-merge baseline in `_finalize_revalidate_stale_branch` (`:4267`) and the post-merge `_finalize_gate_preflight` (`:4284`) gate the primary checkout, never the role worktree. The merged tree is never evaluated, `pre_ok == post_ok` by construction, DEC-0009's "newly red" branch is unreachable in production, and the `REVALIDATE` line records the primary checkout's state as the branch's. The Reviewer's dogfood step (e) — a draft dev PR whose merge of `origin/main` turns the gate red — pushed and opened the PR. Pinned by `test_revalidate_gates_the_merged_worktree_not_the_primary_checkout` (a stand-in `scripts/deploy-gate.py` committed on `main`, red iff `GATE-RED` exists in the tree it resolves from its own location — the real gate's rule). The Reviewer proved the fix shape against that pin: `_run_deploy_gate` gains keyword-only `cwd: Path | None = None` and runs `(cwd or REPO_ROOT) / "scripts" / "deploy-gate.py"` — the *worktree's* copy — with `cwd=str(cwd or REPO_ROOT)`; `_finalize_gate_preflight` threads it; `_finalize_revalidate_stale_branch` passes `wt_path` for both runs. Pre-existing in the FR-0002 helper (no live caller since `aacb473`), but AC-7 is its first caller and AC-7's text names the merged tree. It is a code defect against AC-7 as written; no AC text is needed to make it one.

- **E5 — gate side effects inside the worktree.** Once the gate runs in `<wt>` it does two things it did in the primary checkout until now: unless `--status-only`, it rewrites the tracked `specs/INDEX.md` (`deploy-gate.py:294–300`) and appends its `gate.run` record to `<wt>/specs/_metrics/<month>.ndjson` (`:142–146`; `metrics_log.METRICS_DIR` also roots from `__file__`, so the worktree's copy of the gate writes the worktree's copy of the log). The revalidate step runs *after* `_finalize_commit_step` (FR-0006 AC-1) and before the push, so neither write is committed by that finalize: both stay as unstaged tracked modifications in the implementation worktree. AC-1's post-approve fast-forward then refuses — `_ff_push_impl_onto_rev` checks `_rev_worktree_dirty_paths(<impl wt>)` and prints `uncommitted tracked changes (specs/INDEX.md, specs/_metrics/2026-09.ndjson …)`, exits 1 (DEC-0009 E3) — so `--revalidate` followed by an approve is refused every time, which is the L25 state AC-1 exists to end. A second `--revalidate` on the same branch is refused the same way by the step's own pre-merge dirtiness check. `--status-only` avoids both writes but also suppresses the `gate.run` record that FR-0002 AC-5's `pr.opened.gate_record_id` would cite; the Reviewer's pin `test_pr_opened_cites_the_post_merge_gate_run_and_reflects_the_merged_head` asserts the citation and cannot see whether the record exists.

Three facts decide the shape.

1. **The record the post-merge run would write is orphaned wherever it lands in the worktree.** The dispatcher's `_metrics_emit` writes `pr.opened` through the *primary checkout's* `metrics_log` (its `REPO_ROOT` is `dispatch.py`'s own location), so the citing record and the cited record are in different files on different trees. The worktree's month file reaches `main` only if the append is committed on the role branch — which FR-0006 AC-3 forbids the dispatcher to do on the agent's behalf ("It never runs `git add`") and FR-0013's Out of scope restates ("Auto-staging anything on the agent's behalf … stands"). Before K6 the record went to the primary checkout's log beside `pr.opened` — coherent as metrics, wrong as a gate. There is no shape in which the record is both written by the worktree's gate and reliably joinable to `pr.opened` without either a dispatcher commit or a `deploy-gate.py` / `metrics_log.py` change, and FR-0013's Out of scope already names the latter as its own FR ("Teaching the deploy gate to write its metrics record somewhere other than the worktree copy — the other half of Project A L36").
2. **On today's `main` no live finalize path writes a preflight `gate.run`.** FR-0002's changelog records it: "`_finalize_gate_preflight` is dead code so `gate_record_id` is always null on the live path." AC-7 is the first caller. Writing nothing on the revalidate path therefore preserves the metrics behaviour the human has today exactly; writing a record is a *new* live behaviour, and this is the last Developer round of the three-cycle budget (AGENTS.md rule 5).
3. **`--status-only` is the gate's own contract for observing without writing.** FR-0002 AC-4 wrote it in for the Stop hook ("a read-only reporting surface by contract; it must not dirty the tree"); `_run_checks` runs every check unchanged and only skips the two writes, so the `(ok, output)` pair AC-7 compares as "same or better" is identical with or without it. The dispatcher's revalidate step is another observer of the same kind. It is also the house convention: every Architect and Reviewer dispatch brief in this project ends with `git restore specs/_metrics/2026-09.ndjson` after the gate run.

The constraint that made the choice non-obvious is the Reviewer's watch-out (ii) and its pin: FR-0002 AC-5 says `gate_record_id` is "the `record_id` of the preflight `gate.run`", and `template/specs/_metrics/README.md` says "`null` when no preflight gate ran". Under this decision a preflight gate *ran* but, by FR-0002 AC-4's own carve-out, emitted no record; `null` is the only honest value (a citation of a record no file contains is worse than `null`), and it is the value every other live path already carries. No FR-0002 sentence changes: AC-4's `--status-only` clause is used as written and AC-5's field is nullable as written. The README sentence is read as "no preflight gate *record*"; that is a doc reading, not a revision (ADR-0001 rule 2's carve-out).

## Decision

FR-0013 is revised in place (`version: 5`, `breaking: true`, `last_breaking_revision: 5`). For `dev`, `mnt` and `bkf` alike — the revalidate step is one code path, `_finalize_revalidate_stale_branch`, and the only per-role difference anywhere in it is the pre-existing draft exemption `_finalize_gate_preflight` keys on `role in ("dev", "bkf")`, which is unchanged:

1. **K6, exactly the Reviewer's fix shape.** `_run_deploy_gate` gains keyword-only `cwd: Path | None = None` (default `REPO_ROOT`, so every existing caller is unchanged) and runs `(cwd or REPO_ROOT) / "scripts" / "deploy-gate.py"` — the worktree's copy, since the gate roots itself from `__file__` — with `cwd=str(cwd or REPO_ROOT)`. `_finalize_gate_preflight` gains the same keyword-only `cwd` and threads it to both of its `_run_deploy_gate` calls. `_finalize_revalidate_stale_branch` passes `cwd=wt_path` for the baseline and the post-merge run. The baseline therefore evaluates the branch's tree (the worktree, verified clean by the step's own dirtiness check immediately before) and the post-merge run evaluates the merged tree; neither ever evaluates the primary checkout.
2. **Both runs `--status-only`.** `_run_deploy_gate` gains keyword-only `status_only: bool = False`; when true it appends `--status-only` to the gate argv. `_finalize_gate_preflight` gains the same keyword-only `status_only: bool = False` and threads it to both of its `_run_deploy_gate` calls (the forced path is unreachable from AC-7, which passes `force=False`; its behaviour is unchanged in every live call). `_finalize_revalidate_stale_branch` passes `status_only=True` on both runs. Consequently the dispatcher's own observation writes nothing: no `specs/INDEX.md` rewrite and no `gate.run` append, in the worktree or the primary checkout. There is nothing to restore, nothing to stage and nothing to commit; the worktree is as clean after the step as the dirtiness check found it before the merge, plus the merge commit on the branch.
3. **No preflight record id is registered on this path; `pr.opened.gate_record_id` is `null`.** `_finalize_revalidate_stale_branch` no longer calls `_gate_metrics_env` for the baseline (it passes `env_extra=None`), and `_finalize_gate_preflight` does not call `_gate_metrics_env` when `status_only=True` (`gate_env = {}`), so `_PREFLIGHT_GATE_RECORD_IDS[(fr_id, role)]` is never set by the revalidate step and `_emit_pr_event` writes `gate_record_id: null` — the value every other live finalize path carries today. The record of the outcome is the `REVALIDATE` line (merged base SHA, `gate=pass` / `red (…)`, naming the draft exemption — DEC-0009 K3) and, for a draft-exempt red gate, the existing `gate_warning_at_finalize` field `_finalize_gate_preflight` saves on the PR record, which is unchanged.
4. **AC-1 is unchanged; no dirtiness tolerance is added.** With item 2 the dispatcher's own runs create no dirt, so `_rev_worktree_dirty_paths` stays as it is for both its callers (AC-1 here; FR-0006 AC-11's Reviewer-worktree sync). An *agent's* own in-session gate run that leaves `specs/_metrics/<month>.ndjson` or `specs/INDEX.md` modified and unstaged is the FR-0006 AC-3 `WARN` case, and AC-1's refusal names the path; the remedy is the staging contract (stage it, or restore it — the house convention). Ignoring `specs/_metrics/**` in the check was considered and rejected (Alternatives, (a')).
5. **The Orchestrator-facing side effect is removed by K6 + item 2, not merely moved.** Before this DEC a `--revalidate` rewrote the *primary checkout's* `specs/INDEX.md` and appended to its metrics log (seen in the Reviewer's dogfood as `M specs/INDEX.md` on `main` after step (e)) — a side effect on a checkout the Orchestrator is working in. After it, the gate runs in the worktree and writes nothing anywhere. Gone, not relocated.
6. **Per-role policy, for the record** (identical by construction; stated per role because the brief asks):

   | Role | Baseline run | Post-merge run | `specs/INDEX.md` afterwards | Metrics append afterwards | AC-1 dirtiness check | `pr.opened.gate_record_id` |
   |---|---|---|---|---|---|---|
   | `dev` | `<wt>/scripts/deploy-gate.py --stage dev --status-only`, `cwd=<wt>` | same, via `_finalize_gate_preflight(cwd=<wt>, status_only=True)`; draft exemption applies (`dev`) | untouched (never rewritten) | none (never written) | unchanged | `null` |
   | `mnt` | same | same; no draft exemption (pre-existing) | untouched | none | unchanged | `null` |
   | `bkf` | same | same; draft exemption applies (`bkf`) | untouched | none | unchanged | `null` |

   Nothing is restored, left, staged or committed by the dispatcher on any row, because nothing is written.
7. **Dry-run is unaffected** (`WOULD-REVALIDATE`, no gate run, AC-9). The `REVALIDATE` line, the "same or better" comparison, the newly-red `ERROR` (DEC-0009 K2), the merge-conflict path and the two-parent merge commit are all as v4 states them.

`breaking: true` under ADR-0001 rule 4: a correct implementation of v4's AC-7 — `0bf67c8` with K6 fixed and nothing else — writes `specs/INDEX.md` and a `gate.run` record into the worktree and registers a record id that `pr.opened` cites; under v5 that is wrong on all three counts, so the implementation must change beyond the defect fix, and the Reviewer's pin `test_pr_opened_cites_the_post_merge_gate_run_and_reflects_the_merged_head` must change with it (Cascade). DEC-0003 and DEC-0009 are the precedents for `breaking: true` on an in-flight FR whose implementation must change.

`tier: architect`: FR-0013 is `ready`, dispatched but unmerged, the Architect owns it; no guarantee the human approved narrows — AC-7 never promised a gate record, FR-0002 AC-4's `--status-only` carve-out and AC-5's nullable field are used as written, and `gate_record_id` is `null` on every live path the human has today. Recorded `proposed`; live for the design (indexer `LIVE_DEC_STATUSES`); ratified when FR-0013's PR merges beside DEC-0008, DEC-0009 and DEC-0010. What Neil ratifies, concretely: (a) the dispatcher's revalidate gate runs observe without writing, so a merge-induced regression is recorded on the `REVALIDATE` line and (draft-exempt) on the PR record, not as a `gate.run` metrics record; (b) the metrics trace for those runs is deferred to the relocation follow-up (FR-0013 Notes name it for the Chief of Staff to park), after which the post-merge run drops `status_only=True` and registers its record id — one keyword flip and one line, no AC change beyond deleting the `null` sentence. If Neil wants the record now, the route is that follow-up landing first, not a change to this DEC. Rule 5 does not apply — FR-0013's identity is unchanged.

## Alternatives considered

- **(a) The Reviewer's lean: baseline `--status-only`, post-merge full, `git restore specs/INDEX.md`, tolerate the append.** Rejected: the tolerated append is a modified tracked file in the implementation worktree, which is precisely what AC-1's fast-forward refuses (`uncommitted tracked changes (specs/_metrics/2026-09.ndjson)`, rc 1) — so `--revalidate` then approve fails every time the month file is tracked, i.e. every time but the first run of a month; a second `--revalidate` is refused by the step's own dirtiness check; and the record is orphaned (Context, fact 1) — `pr.opened` would cite an id that no committed file ever contains. AC-5(b) exempts a *committed* append at the mnt footprint check (`main...branch` sees committed history only; Notes finding (a)); it says nothing about an uncommitted one, and it does not exist for `dev` or `bkf`.
- **(a') As (a) plus `_rev_worktree_dirty_paths` ignores `specs/_metrics/**`.** Rejected: `git merge --ff-only` is a checkout and refuses to overwrite a locally modified file when the incoming commits touch it — and the Reviewer's branch touches the month file whenever the Reviewer staged its own gate runs' append, which the staging contract leaves to the Reviewer. The refusal then arrives as `fast-forward … failed: Your local changes … would be overwritten` instead of the clear dirtiness message — the same L25 state with a worse explanation — and when the fast-forward does succeed the append persists as unstaged dirt into the next finalize (FR-0006 AC-3 `WARN`) and never reaches `main`. It also changes `_rev_worktree_dirty_paths` for FR-0006 AC-11's caller, a cascade this FR has no business starting in its last round. The record stays orphaned either way.
- **(c) Post-merge full, restore `specs/INDEX.md`, stage and commit the append as a dispatcher commit.** Rejected: FR-0006 AC-3 is literal — "It never runs `git add`" — and FR-0013's Out of scope restates it; carving out "the dispatcher's own artifact" is a `neil`-tier revision of a merged FR (DEC-0002 / DEC-0005 / DEC-0007 precedent) with no human in the loop in a headless last round. It also puts a third commit on the branch after the merge commit, so the tip is no longer the two-parent merge the AC-7 pins assert, `commits_ahead` moves in `test_pr_opened_cites…` and `test_refreshed_pr_record…`, and the PR carries a metrics-only commit the agent never made. Its one merit — AC-5(b)'s L36 shape produced by the dispatcher itself — is not worth that.
- **(c2) Post-merge full, then the dispatcher moves the appended line(s) into the primary checkout's log (`metrics_log.append`) and restores the worktree's month file.** Rejected: it is the record relocation FR-0013's Out of scope defers, done from the dispatcher side — new machinery (snapshot the month file's length, read the tail, re-append, restore or delete) with its own failure modes, all landing in the last Developer round with no pin the Reviewer could `# covers` beyond AC-7. It is the right *destination* (the record beside `pr.opened`, as before K6) but the wrong FR and the wrong round; it becomes the one-keyword flip in "what Neil ratifies" (b) once the follow-up lands in the gate.
- **Relocate via a `deploy-gate.py` / `metrics_log.py` log-directory override, in this FR.** Rejected: `deploy-gate.py` is a human-approval file in this FR's `reads:`, not its `owns:`; `metrics_log.py` changes are explicitly out of scope; FR-0013's Out of scope already names this as its own FR. Recorded in FR-0013 Notes as the follow-up for the Chief of Staff to park.
- **Keep the gate in the primary checkout and compare its state before and after the merge.** Rejected: it is K6 — the primary checkout's tree does not change when the worktree merges `origin/main`, so `pre_ok == post_ok` always and AC-7's "against the merged tree" is never true. The dogfood showed it pushing a newly red draft.
- **Both runs `--status-only` but keep `_gate_metrics_env` so `pr.opened` cites the id it would have had.** Rejected: a citation of a record that was never written is a lie in the log; `null` is the field's documented value when there is no record to cite.
