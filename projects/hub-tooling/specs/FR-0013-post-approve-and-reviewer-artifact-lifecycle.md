# FR-0013: Post-approve and Reviewer-artifact lifecycle in `finalize` and `wave`

## Why

FR-0006 made the dispatcher own the commit and the rework sync. The Project A FR-0001 wave ran past the point FR-0006 reached and found the next seven mechanical gaps, all in `finalize` and `wave`, all paid for by hand. On the round-2 approve, the Reviewer's commits — its adversarial tests and its `REVIEW.md` — sat on `claude/rev-FR-0001` and were not in the PR, because the wave merges the Reviewer branch into the dev worktree only *before* a rework round; the Orchestrator fast-forwarded, re-ran the gate and pushed by hand (L25). `finalize --role rev` overwrote the Reviewer's own 11 KB review with the 3 KB final message (L17). The verdict extractor missed `## FR-0001 review — **Request changes** (round 1 of 3)` because its regex needs the marker at line start, and posted `comment` (L16). A Reviewer run as an in-harness subagent writes no `_dispatch/FR-XXXX.rev.log`, so `finalize --role rev` cannot be used for it at all (L15). The maintainer footprint check refused to push an approved branch twice: once because the deploy gate had appended to `specs/_metrics/2026-09.ndjson` inside the worktree (L36), and once because the Reviewer's own tests had been fast-forwarded in, which the terminal state requires (L39) — today's round-2 maintainer run hit the same wall a third time on a crossing DEC-0036 had explicitly authorised. PR #4's CI was red purely because its branch predated PR #5's merge; merging `main` in turned it green with no code change (L46). And `--rounds` defaults to 1, so the three-cycle budget in `CLAUDE.md` goes unused and a request-changes verdict ends the wave (L3). Together these cost about twenty-five to thirty minutes of Orchestrator time per FR — roughly five to six hours across the twelve remaining Project A FRs — plus the loss of the review text FR-0008's gate-evidence model depends on.

## What

After this FR lands, an approve is a terminal state the dispatcher can reach on its own: it fast-forwards the implementation branch onto the Reviewer's tip and pushes, so the PR carries the round-N tests and review. The Reviewer's own `REVIEW.md` survives — the dispatcher synthesises one only when the branch carries none. A verdict can be declared rather than sniffed: a `Verdict:` first line is authoritative, a marker anywhere in the first heading is accepted, and `--verdict-file` makes a subagent-run Reviewer finalizable. The maintainer footprint check stops refusing work it should not refuse: Reviewer-owned paths landed by the `rev` role, `specs/_metrics/**`, and crossings the operator declares and the dispatcher verifies to be content-free. A branch whose base has moved gets a rebase-and-revalidate step rather than a red CI mystery. And the Dev-Reviewer budget defaults to two rounds.

## Acceptance criteria

Each AC must be independently testable. Number them; the numbers are stable for the life of the FR.

- **AC-1:** **An approve fast-forwards the implementation branch onto the Reviewer's tip and pushes it.** When `finalize --role rev --apply` resolves the verdict to `approve`, the dispatcher fast-forwards the implementation branch for that FR — `claude/dev-<FR>` if it exists, otherwise `claude/mnt-<FR>` — onto `claude/rev-<FR>` with `git merge --ff-only`, then pushes it, so the open PR's head carries the Reviewer's commits. It prints one `FF-PUSHED` line naming both branches and the new head SHA, and refreshes the PR record's `head_sha`. When the implementation branch is already at or ahead of the rev tip, nothing is merged and one `NOTE` line says so. When no implementation branch exists, the step is skipped with one `NOTE`. When the fast-forward is refused — the branches have diverged, the implementation worktree is missing or carries uncommitted tracked changes, the merge or the push fails — the review stays posted, the implementation branch and its worktree are untouched, the `ERROR` line states that the review was already posted (so a re-run is understood to re-post it), and `finalize` exits non-zero: the terminal state the approve requires was not reached, and `wave` must not report the FR as completed with the Reviewer's commits off the PR (Project A L25). The "nothing to do" `NOTE` cases exit 0. When the fast-forward succeeds, the implementation role's PR record additionally gains `ff_commits`: the full SHAs of the commits it brought in (`<impl-tip>..<rev-tip>` at the moment of the merge), unioned with any earlier value so a round-2 approve keeps round 1's; the refused and nothing-to-do cases leave the key as it was. The PR record is dispatcher state in `_dispatch/`, not a metrics record, so AC-10 is unaffected. Verified against a temporary repository with `gh` stubbed, for the dev case, the mnt case, the already-current case, and the refused case (exit code, review posted, branch untouched).

- **AC-2:** **The Reviewer's own `REVIEW.md` is kept; one is synthesised only when absent.** `finalize --role rev` writes and commits a synthesised `REVIEW.md` only when `claude/rev-<FR>` carries none *and* the Reviewer worktree has none staged. When the Reviewer committed or staged its own, that file is left byte-for-byte untouched, is committed as part of the staged index by the existing commit step if it is not yet committed, and finalize prints one `REVIEW-KEPT` line naming the path and its byte count. In both cases, after finalize `_read_review_md_on_branch(<FR>)` returns a non-empty body and `_prepare_dev_worktree_for_rework`'s precondition passes, so the guarantee FR-0006 AC-6 made is preserved by the other route. A committed or staged `REVIEW.md` whose content is empty or whitespace-only is not a review and counts as absent: the synthesised one replaces it (`REVIEW-WRITTEN`, or `WOULD-WRITE-REVIEW` in dry-run) and one `WARN` line says the empty file was replaced, so the non-empty-body guarantee holds in every case. `_read_review_md_on_branch` and the byte count decode the committed file as UTF-8 — the encoding `_materialise_review_md` writes and the Reviewer's editors use — never the host locale, so the body the rework brief and `_resolve_rework_verdict` see is the file's text on every host. **This AC implements DEC-0001 (`revises: FR-0006`, `breaking: true`), which flips FR-0006 AC-6's always-overwrite rule; FR-0006 is at `version: 2` with `last_breaking_revision: 2` and its AC-6 text is amended accordingly.** Verified for: agent committed a `REVIEW.md`, agent staged one uncommitted, agent produced none, agent committed an empty one, and a re-run of finalize over each. **Revised by DEC-0022 (v7, breaking):** a `REVIEW.md` byte-identical to the one at `git merge-base claude/rev-<FR> main` is inherited, not the Reviewer's own, and counts as absent. The synthesised review replaces it, with one `WARN`. Implemented by FR-0018 AC-5. **Revised by DEC-0024 (v8, breaking), following DEC-0023:** the rule above applies to the round's library file, `specs/_reviews/<FR>-r<N>.md`. The Reviewer's own non-empty root `REVIEW.md` is kept byte for byte by filing it there and removing it from the root in one commit (`REVIEW-KEPT`). Otherwise the synthesised body is filed (`REVIEW-WRITTEN`). A re-run with the round already filed adds no commit. The inherited-file comparison is unchanged, but an inherited root file is now never filed and never removed. It is implemented by FR-0025 AC-1, not FR-0018 AC-5.

- **AC-3:** **A declared verdict beats a sniffed one, and the marker is accepted anywhere in the first heading.** `_extract_review_verdict` resolves in this order: (1) the text's first non-empty line matching `Verdict:\s*(approve|request-changes)` case-insensitively; (2) an `approve` / `request changes` marker anywhere inside the first Markdown heading of the text, in any inline emphasis; (3) today's existing patterns, with today's earliest-match tie-break; (4) `comment`. The body returned is the full text verbatim in every case, unchanged from today. Verified with `## FR-0001 review — **Request changes** (round 1 of 3)` (returns `request-changes`, which today returns `comment`), a `Verdict: approve` first line followed by a heading saying the opposite (returns `approve`), each of today's matching shapes (unchanged results), and text with neither (returns `comment`).

- **AC-4:** **`--verdict-file` makes a subagent-run Reviewer finalizable.** `finalize --role rev --verdict-file <path>` reads that file's contents as the Reviewer's final text, applies AC-3 to it, and does not require `_dispatch/<FR>.rev.log` to exist. The flag takes precedence over the log when both are present, and finalize prints one `VERDICT-FROM-FILE` line naming the path. A missing or empty `--verdict-file` is one `ERROR` line and a non-zero exit with no push, no `gh` call and no PR record written. Without the flag and without a log, the existing "no reviewer log" error is unchanged.

- **AC-5:** **The maintainer footprint check exempts Reviewer-landed paths and the metrics log.** `mnt_footprint_violations` no longer reports, and `finalize --role mnt` no longer refuses on: (a) any path whose every change on `<base>...<branch>` was introduced by a commit on `claude/rev-<FR>` that was fast-forwarded in (identified by commit provenance, not by path pattern alone); (b) `specs/_metrics/**` in every case. Each exemption prints one `NOTE` line naming the path and which rule exempted it. Paths outside `owns:` that neither rule covers still produce the refusal exactly as today. **Provenance for (a) is the dispatcher's own record of what it fast-forwarded in** — the `ff_commits` AC-1 writes on the implementation role's PR record — and nothing else: a path is exempt only when every commit touching it on `<base>..<branch>` is in that set. Membership in `claude/rev-<FR>`'s ancestry is not provenance: once the implementation branch sits on the Reviewer's tip, every commit on it is such an ancestor, including anything the maintainer committed before the Reviewer branched, so an ancestry test exempts everything and is wider than the path-pattern form the Open question rejected. With no record, or with any touching commit outside it (the maintainer wrote the path, edited it after the fast-forward, or committed it before the Reviewer branched), the path is not exempt. **Revised by DEC-0015 (v6, breaking):** exemption (a) never applies to a path matching `MNT_PROTECTED_GLOBS`. Such a path is outside `owns:`, so it stays a violation and refuses, whoever committed it. One line in place of (a)'s `NOTE` says why. (b) and AC-6 are unchanged. Implemented and tested under FR-0015 AC-1. Verified with a mnt branch carrying: an owned path, a Reviewer test landed by fast-forward through AC-1's step, a `specs/_metrics/*.ndjson` append, and an unowned source file committed before the Reviewer branched (the last one alone refuses); and, adversarially, the same `tests/**` path written by the maintainer, a Reviewer-landed path the maintainer then edited, and a Reviewer branch merged into the maintainer branch by hand with no record (none exempt).

- **AC-6:** **A declared crossing is exempted only when the dispatcher can prove it is content-free.** `finalize --role mnt` accepts a repeatable `--allow-crossing <glob>`. For each glob, the dispatcher verifies that `git diff --ignore-cr-at-eol --ignore-all-space <base>...<branch> -- <glob>` is empty; when it is, the matching paths are exempt from the footprint check and one `CROSSING-ALLOWED` line names the glob and the file count. When the diff is *not* empty, the glob is not exempted, one `ERROR` line names the glob and states that the crossing carries content, and finalize refuses as it would without the flag. A glob that matches nothing produces one `WARN` and no exemption. The glob is validated by the same rule `spec_footprint._validate_glob` applies, so an absolute path or a `..` segment is refused. Verified with a line-ending-only renormalisation of `.claude/commands/**` (allowed) and the same glob with one real edit (refused).

- **AC-7:** **A stale branch is revalidated rather than left red.** `finalize` for `dev`, `mnt` and `bkf` checks, before the push, whether `origin/main` contains commits the branch does not. When it does, and `--revalidate` is passed (or `wave` reaches finalize for an FR whose `depends_on` PR merged during the run), the dispatcher merges `origin/main` into the role worktree with an ordinary merge, re-runs `_finalize_gate_preflight` against the merged tree, and proceeds only if the gate result is the same or better than before the merge; a merge conflict or a newly red gate is one `ERROR` line, a non-zero exit, no push, and the worktree left with the conflict in place for a human. Without the flag, a stale branch is one `WARN` line naming the count of missing commits and the `--revalidate` remedy, and finalize proceeds as today. One `REVALIDATE` line records the merged base SHA and the gate outcome. **Where the gate runs and what it may write (DEC-0011):** both gate runs — the pre-merge baseline and the post-merge re-run — execute in the role worktree, as `<wt>/scripts/deploy-gate.py` with `cwd=<wt>` (the gate roots itself from its own location), so the tree evaluated is the branch's before the merge and the merged tree after it, never the primary checkout's; and both run `--status-only`, so the dispatcher's own observation writes nothing — no `specs/INDEX.md` rewrite and no `gate.run` append, in the worktree or the primary checkout — and the worktree is as clean after the step as the dirtiness check found it before the merge (plus the merge commit), so AC-1's later fast-forward is never refused by the dispatcher's own side effects. Because a `--status-only` run emits no `gate.run` record (FR-0002 AC-4), this path registers no preflight record id and `pr.opened.gate_record_id` is `null`, exactly as on every other live finalize path today; the `REVALIDATE` line and, for a draft-exempt red gate, the existing `gate_warning_at_finalize` field on the PR record are the record of the outcome. The policy is identical for `dev`, `mnt` and `bkf`. **Revised by DEC-0022 (v7, breaking):** a merge conflict confined to `specs/INDEX.md` and `REVIEW.md` is resolved by the dispatcher instead of being left for a human. The index is regenerated by the worktree's `scripts/index-specs.py`, `REVIEW.md` takes the branch's side, the merge is concluded with `git commit --no-edit`, and one `MERGE-RESOLVED` line is printed. Any other conflict, a missing worktree indexer, or a failing indexer is still one `ERROR` with the conflict left in place. Clean merges are unchanged. Implemented by FR-0018 AC-4. **Revised by DEC-0024 (v8, breaking):** the carve-out applies only when every conflicted path is `specs/INDEX.md`. A `REVIEW.md` conflict is left for a human like any other; none arises once branches stop carrying the root file (DEC-0023).

- **AC-8:** **`wave --rounds` defaults to 2.** The `--rounds` default is 2, so a request-changes verdict drives one automatic rework round inside the three-cycle budget without human involvement. The existing range check (1..`REVIEW_CYCLE_BUDGET`) and the force-escalate behaviour at budget exhaustion are unchanged, `--rounds 1` still reproduces today's single-pass behaviour exactly, and the wave's opening line and the `dispatch.wave` record's `rounds_ran` reflect the effective value. The help text states the new default.

- **AC-9:** **Dry-run previews every new step and mutates nothing.** Without `--apply`, finalize prints `WOULD-FF-PUSH` (AC-1), `WOULD-KEEP-REVIEW` or the existing `WOULD-WRITE-REVIEW` (AC-2), `WOULD-ALLOW-CROSSING` (AC-6) and `WOULD-REVALIDATE` (AC-7), and reports AC-6's content-carrying refusal as `WOULD-REFUSE` rather than an error. After a dry run, every branch tip, every worktree's index and working tree, `_dispatch/` and `specs/_metrics/` are byte-identical to before. Verified by snapshotting `git for-each-ref` and `git status --porcelain` in each worktree before and after.

- **AC-10:** **No history is rewritten and existing behaviour is preserved.** Nothing in this FR runs `merge` without `--ff-only` on a role branch except AC-7's explicit `origin/main` merge into the implementation worktree; no `rebase`, no `reset --hard`, no `checkout -f`, no forced push, in any path. Every test that passed before this FR still passes except three merged tests, each changed only as its DEC bounds and each still pinning the behaviour it pinned before: the FR-0006 AC-6 overwrite test, which DEC-0001's cascade re-points (DEC-0008 bounds the edit); FR-0014's dry-run byte-identity guard, which DEC-0007 narrows to an explicit `rounds=1`; and FR-0002's `pr.review` finalize test, whose `subprocess.run` stub DEC-0010 makes order-agnostic because AC-11 runs `git show-ref` before `gh pr review`. The `pr.opened` / `pr.refreshed` / `pr.review` records still validate, `commits_ahead` and `head_sha` on the refreshed record reflect the post-fast-forward state, and no new metrics record kind or field is introduced.

- **AC-11:** **The rev leg resolves the implementation role the way AC-1 does, so a maintainer-mode FR can be reviewed and approved through `finalize --role rev`.** The implementation branch and role for an FR are `_implementation_branch_for_fr`'s answer — `claude/dev-<FR>` if it exists, else `claude/mnt-<FR>`, else none — and every point on the rev leg of the bare commands that today names the Developer's branch or PR record resolves through it: `_base_branch_for_role("rev")` (a fresh Reviewer worktree is based on the implementation branch, so a dispatched Reviewer of a maintainer-mode FR sees the maintainer's diff; `main` only when neither exists); `_rev_sync_plan` / `_fast_forward_rev_worktree` (a reused Reviewer worktree is fast-forwarded onto the implementation tip); `_finalize_base_branch("rev")` (the Reviewer branch is measured against the implementation branch); the `rev` tick's eligibility check; `cmd_finalize`'s dry-run parent-PR lookup; and `_finalize_rev`, which resolves the parent PR from the implementation role's PR record (`_dispatch/<FR>.dev.pr.json` if it exists, else `<FR>.mnt.pr.json`) and, failing that, from the open PR for the implementation branch, and whose "no parent PR" error names that branch and the matching `finalize --role <impl-role> --apply` remedy. `wave` is unchanged (it never dispatches `mnt`). When only `claude/mnt-<FR>` and `<FR>.mnt.pr.json` exist, `finalize --role rev --apply` posts the review against the maintainer's PR and, on an approve, AC-1 fast-forwards `claude/mnt-<FR>` and records `ff_commits` on `<FR>.mnt.pr.json`; when `claude/dev-<FR>` exists, every line of output and every record is byte-identical to today (AC-10). Verified against a temporary repository with `gh` stubbed for: a mnt-only FR (worktree base, review posted against the mnt PR number, fast-forward and record), a dev-only FR (unchanged), both present (dev wins), and neither (the existing errors, naming both candidates).

## Out of scope

- Any change to `template/scripts/metrics_log.py` or to the metrics schema. AC-10 is explicit that nothing new is emitted.
- Merging the PR, setting a GitHub approval state on the owner's own PR, or giving the factory a bot identity (Project A L24). The human still approves and merges; FR-0012 restates that contract in the commands.
- Auto-staging anything on the agent's behalf. FR-0006 AC-3's report-never-add rule stands; AC-2 here commits a staged `REVIEW.md` only through the existing verbatim commit step.
- Teaching the deploy gate to write its metrics record somewhere other than the worktree copy (the other half of Project A L36). AC-5 exempts the path at the check; relocating the write is a `deploy-gate.py` change and its own FR. DEC-0011 depends on that FR for the other direction too: until the gate can write a dispatcher-invoked worktree run's record beside `pr.opened`, AC-7's revalidate runs are `--status-only` and cite no record (Notes, follow-up (i)).
- Declared gates and phase-boundary enforcement — FR-0008, which reads the review artifact this FR preserves.
- Permission grants of any kind — FR-0009 and FR-0010.
- Classifying a run that ended with a question as `stopped-needs-input` (Project A L28), and the `wave --follow` / detached-run primitive (L2). Neither is promoted.
- Any change to what the Reviewer writes. FR-0012 owns the command text; this FR only stops destroying the artifact.

## Open questions

- **Q:** Should AC-1's fast-forward-and-push happen when the deploy gate was only draft-exempt (red but tolerated)?
  - **Default:** Yes, push. The PR is a draft either way and a human merges it; withholding the Reviewer's tests from a draft PR is the state L25 describes and is strictly worse for the reader.
- **Q:** Should AC-5(a) identify Reviewer-landed paths by commit provenance or simply exempt `tests/**` and `REVIEW.md`?
  - **Default:** Commit provenance, as written. A path-pattern exemption would let a maintainer write `tests/**` directly and pass a check whose whole purpose is that it cannot. The path-pattern form is the fallback if provenance proves unreliable across the fast-forward; record it under `## FINDINGS` before changing the AC.
  - **Resolved 2026-09-21 (DEC-0009).** The trigger fired — the Reviewer's round-1 `## FINDINGS` recorded that provenance *by ancestry of `claude/rev-<FR>`* is vacuous after the fast-forward — but provenance itself did not prove unreliable, only that mechanism did: the dispatcher performs the fast-forward (AC-1) and therefore knows exactly which commits it brought in. AC-5 now names that record (`ff_commits`) as the provenance source. The path-pattern fallback stays rejected for the reason above.
- **Q:** Should `--allow-crossing` be declarable on the FR instead of on the command line?
  - **Default:** Command line (AC-6). An FR-frontmatter key would touch the FR template and the indexer, which is FR-0008's footprint, and the crossing is a property of one maintainer run rather than of the requirement. The decision that authorises the crossing still lives in a DEC; the flag is how the Orchestrator asserts it, and AC-6's content-free proof is what makes the assertion safe.
- **Q:** Should AC-7 revalidate automatically rather than behind `--revalidate`?
  - **Default:** Behind the flag for `finalize`, automatic inside `wave` when a dependency merged during the run. An unattended merge into a worktree a human may be looking at is the kind of surprise the FR-0006 "never rewrite history" rule exists to avoid.
- **Q:** Does `--rounds 2` by default risk burning a second spawn on an FR whose spec is wrong?
  - **Default:** Accept it. The three-cycle budget in `CLAUDE.md` exists precisely to buy one automatic round, the force-escalate path already fires at budget exhaustion, and in the FR-0001 wave round 2 turned a request-changes into an approve.
