- **CRLF decision: replace in place, upheld.** The line-wise rule accepts a well-formed CRLF block without a CRLF-specific branch. Outside bytes are rebuilt from the original line list, so they are byte-identical. Inside the block the bytes become the template's LF. A second run is up to date. This is the safe direction: one block, and the stale CRLF copy is not left behind as project lines.
- **Ruling on mangled marker lines: damaged, not well-formed.** A marker line with trailing spaces or tabs, or with a leading BOM, is **not** a marker. Only the line terminator is stripped before comparing. With the other marker intact the file holds exactly one marker, so it is damaged: one drift line, bytes untouched, identical on a second run. I endorse the strict rule. The marker line itself says "do not edit", and a tolerant match would widen what counts as "managed". When **both** markers are mangled, the file reads as marker-free and a fresh block is inserted on top. Every original byte stays below it and the result is stable. That conforms to AC-5's "Present without markers", but the near-marker pair survives below as project lines (FINDINGS F6).

Candidate for the Architect: replace a known-prior-template file wholesale, or drop comment-only lines from the NOTE.
- **F3.** The `--upgrade` `--help` epilog still omits `.gitattributes`, seed-only `pytest.ini` and stack rendering.

- **F6 (new).** When **both** marker lines are mangled (for example, trailing whitespace on each), neither is a marker. The file reads as marker-free, so a fresh block is inserted and the near-marker pair stays below as project lines. That conforms to AC-5 and loses no byte, but it leaves a stale lookalike block. Candidate for the Architect: treat a line that equals a marker after `strip()`/BOM removal but is not exact as damage (drift, no write).
- **F7 (new, minor).** `_gitattributes_duplicate_lines` (`bootstrap.py:1485`) still finds the block with a raw `str.find` of the LF marker text. It works because it runs only on `new_text`, which always holds the template's LF block. However, a project line that merely *contains* the marker text earlier in the file could anchor the NOTE's span wrongly. This affects only the informational NOTE and changes no bytes.
- **F8 (new, minor).** A non-UTF-8 `.gitattributes` (for example, UTF-16 from an editor) would raise `UnicodeDecodeError` in `run_upgrade` rather than report drift. This is untested and outside AC-5's listed cases.
