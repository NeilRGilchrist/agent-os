## The amended AC-1 and AC-3 against the code

**The rule.** `_dir_list` runs `_validate_glob` on every entry first, then raises `LayoutInvalid` for any entry whose `PureWindowsPath(entry).drive` is non-empty. The message reads `.agent-team/layout.yaml: gate.<key> entry '<entry>' has a drive or UNC root; directories must be relative to the footprint root`. It names the file and `gate.<key>`, as AC-1 and `solution_space.open` require.

**Layout only.** `spec_footprint.py` is untouched since `ab588d9`. My `test_the_drive_rule_is_layout_only_and_owns_is_unchanged` puts the same `C:/x` in an FR's `owns:` and in `gate.test_dirs`. `--validate` reports exactly one error, the layout's. With the layout removed, the same tree validates. That satisfies `solution_space.fixed` line 2.

**Drive forms that pass `_validate_glob`** are refused only by the new rule. All are pinned under both keys:
- the Developer's `C:/x` and `c:x`;
- my `C:`, `z:/`, `C:.`, `c:/Mixed/Case` and `1:x`.

`PureWindowsPath` treats any single character before `:` as a drive.

**UNC forms never reach the drive check.** Each is refused earlier, by one of the two `owns:` rules:
- `//server/share/x`, `//server` and `//?/C:/x` hit the leading-`/` absolute rule;
- `\\server\share` hits the backslash rule.

Every one still raises `LayoutInvalid` naming `gate.<key>` (`test_unc_forms_are_refused_by_one_rule_or_the_other`, 6). So the UNC half of the drive check is defensive and unreachable in practice. AC-1's example `//server/share/x` is refused with the `is absolute` message, not the drive message. The outcome is what AC-1 requires. See F-1.

**No false positives.** A colon anywhere but the drive position is allowed, and the entry stays under the root. `test_a_colon_outside_the_drive_position_is_allowed_and_stays_under_root` checks `lib/C:/x`, `ab:c`, `a/b:c` and `:x`; `path.relative_to(layout.root)` holds for each.

## Coordinator check: the `@implements FR-0023` tags in `template/scripts/`

**Finding: it cannot reach a bootstrapped project's gate as a failure. No change requested.**

The `@covers` literal behind FR-0027's K-1 broke projects because of three things at once:
- the template's tests ride into projects under `tests/`, which every gate scans by default;
- an unknown FR in `@covers` is a hard `covers-unknown-fr` failure at every stage;
- it named an FR the project does not have.

`@implements` differs on two of those three:
1. **Not scanned.** `template/scripts/*.py` land in a project's `scripts/`. The gate's default `source_dirs` is `[src]`, so `scripts/` is never scanned unless a layout lists it, and `layout.yaml.example` says "Do not list `scripts/`".
2. **Warning class only.** Check 4, the `@implements` cross-reference, emits warnings only (`deploy-gate.py`: "# 4. @implements cross-reference (warnings only)"). An unknown-FR `@implements` prints `@implements references unknown FR …` and never sets a failure class.

The pattern is also not new.
- At `ab588d9`, 338 lines in `template/scripts/` already carried a hub-tooling `@implements` tag. At `b7594c9` there are 339.
- FR-0023's own tags were already in `deploy-gate.py`, `index-specs.py`, `spec_footprint.py` and the `project_layout.py` docstring at `ab588d9`. `b7594c9` adds one more, on `_dir_list`.
- FR-0023's Open question already decides this default: the tags count for hub-tooling through `source_dirs`, and no other project lists `scripts/`.

`test_template_scripts_implements_tags_never_fail_a_project_gate` pins both halves. It copies every `template/scripts/*.py` into a project with one merged, covered FR and runs the gate at `--stage full`:
- **with no layout:** exit 0, and `FR-0023` is never mentioned;
- **with `gate: {source_dirs: [scripts]}`**, the case the example warns against: still exit 0, with only the `@implements references unknown FR FR-0023` warning.

The dogfood repeats the first half on a real bootstrap: 0 mentions of `FR-0023`.
