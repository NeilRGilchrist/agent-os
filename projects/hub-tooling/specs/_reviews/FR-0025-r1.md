## Ruling: AC-1 vs AC-5 on a legacy root file the Reviewer overwrote

**The Developer's reading is correct.** When the merge-base carries a legacy root `REVIEW.md` and the Reviewer overwrote it, the filing commit files the Reviewer's blob and puts the merge-base blob back at the root, so the branch's net change to `REVIEW.md` against the merge-base is nil.

- AC-1's "removes a pending root file" is written for the normal case. Read literally here, it makes every Reviewer branch delete `main`'s legacy file. Two such branches then merge cleanly (delete/delete), but `main` loses the file, which breaks AC-5's "the legacy file is unchanged".
- Out of scope bars "deleting or moving a legacy root `REVIEW.md` from any dispatcher … path"; the migration is a human commit on `main`. A literal deletion would be that.
- DEC-0023 Decision 3 makes the inherited legacy file the one exception to "the root file never reaches a pushed branch". Restoring the merge-base blob is the only way to honour both halves.
- The restore uses the merge-base's blob, not `main`'s current one, so it also merges cleanly if `main` later changed or migrated the legacy file. The "Reviewer wrote its own" commit still shows the overwrite in history; the net diff is nil.

`test_own_review_over_a_legacy_root_file_is_filed_and_the_legacy_file_is_left_as_found` and `test_two_frs_merge_cleanly_over_a_legacy_root_review_and_leave_it_unchanged` pin it. I recommend the Architect add one clarifying sentence to AC-1 (FINDINGS); no change is needed for this round.

**Edge choices:** an empty pending root file filed by the collision rule at max+1 with one `WARN` is consistent with "a filed round is never overwritten", and `REVIEW-KEPT` naming round N in the nothing-to-file case is what AC-1 asks for. Accepted. The *empty library file* case is not covered by either and is escalated (N1).

## Kick-back items

**B1 (FR-0025:AC-3, blocking): the rework precondition refuses a correct sync on a `core.autocrlf=true` host.** `_prepare_dev_worktree_for_rework` (`dispatch.py`, the `_working_file_blob_sha(review_path, dev_wt) != review_blob` check) hashes the dev worktree's file with `git hash-object`, which applies the clean filter. Under `core.autocrlf=true` a blob that contains CRLF checks out unchanged, byte for byte, and `git status` is clean, but `hash-object` hashes the LF-normalised text, so the sha differs and the round stops with `specs/_reviews/FR-0001-r1.md not present in dev worktree after sync`. Git for Windows defaults to `core.autocrlf=true`, this host has it globally, and the FR's own fixed line names CRLF. The Developer's tests set `core.autocrlf=false` in every repository, which hides it.
- Reproduced by `test_rework_precondition_holds_for_a_crlf_blob_on_an_autocrlf_true_host`: the file's bytes equal the blob's, `git status --porcelain -- <path>` is empty, and `ok` is False.
- **What would satisfy me:** a "does this working file hold this blob" check that is true when the file's raw bytes equal the blob's bytes (`_git_blob_bytes`) *or* `hash-object` equals the blob (the LF blob checked out as CRLF case), and false otherwise. Use it in the precondition. My test goes green and `test_rework_precondition_refuses_a_locally_modified_library_file` stays green. Using the same helper in `_materialise_review_md`'s worktree tidy-up fixes N2 as well; that strict `xfail` will then XPASS, so drop its marker.

## ESCALATION

**FR-0025:AC-1, an empty library file for round N.** AC-1 defines "nothing to file" as "no pending root file, and the library file for N already exists on the branch, non-empty", and the collision rule as applying to "a pending root file". Neither covers *no pending root file and an empty (or whitespace-only) `<FR>-rN.md` already on the branch*, which arises only if someone commits one by hand. The implementation falls through to the collision branch and files the synthesised body at max+1 on **every** re-run (r2, r3, r4, …), which breaks "re-running finalize never adds a commit". Pinned by the strict `xfail` `test_rerun_over_an_empty_filed_round_adds_no_commit`.
- **Question:** what does finalize do in that case?
- **Proposed default:** with no pending root file, round N existing at all (empty or not) is "already filed": no commit, one `REVIEW-KEPT` line, plus one `WARN` naming the empty file. A filed round is never overwritten, and a re-run never adds a commit. This does not block B1's rework.
