### Probing `_working_file_holds_blob`

**Can a locally edited file be treated as the blob?** Only when the edit is an end-of-line change that git itself treats as no change.
- A content edit fails both tests. The raw bytes differ, and the clean filter (EOL conversion here) cannot map different text to the same blob.
- The `hash-object` arm accepts exactly what git's own clean filter accepts. So the helper is never looser than git's "unmodified". I pinned that agreement on both sides, parametrised over `core.autocrlf` false and true:
  - `test_tidy_up_removes_the_root_file_only_when_git_itself_sees_it_unmodified`: an LF blob whose working copy is rewritten with CRLF only. With autocrlf off, git reports it modified, and the tidy-up leaves it, byte for byte. With autocrlf on, git reports it clean, and the tidy-up removes it.
  - `test_rework_precondition_accepts_an_eol_only_variant_only_when_git_does`: the same on the dev side. The precondition passes exactly when `git diff --name-only -- <path>` is empty.
- One case is conservative, not loose. A CRLF blob whose working copy was rewritten to LF fails both tests, so it is refused. git, too, reports it modified under autocrlf.

**Does the tidy-up ever delete something it shouldn't?** No.
- It deletes the root file, or restores the merge-base blob over it, only when the file holds the pending blob. That blob is already committed on the branch and filed byte for byte in the library, so nothing is lost but a line-ending representation git considers equal.
- It never runs for an inherited file (`pending is None`), an untracked file, or the dry-run.
- A file edited after staging is left in place. Pinned by `test_filing_moves_the_staged_blob_not_the_edited_working_tree_file` and by the autocrlf-off case above.
- `_git_blob_bytes` returning None on a git failure compares unequal to any file, so a read failure keeps the file.

**Bootstrapped-project configuration.** `test_bootstrapped_attributes_on_an_autocrlf_true_host_file_tidy_and_sync` runs with `* text=auto eol=lf` (every bootstrapped project) on `core.autocrlf=true`. The Reviewer's CRLF file is stored and filed as the LF blob, leaves the rev worktree, and the rework sync is accepted.
