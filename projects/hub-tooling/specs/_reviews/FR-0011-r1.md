## Kick-back items (what is wrong; what would satisfy me)

1. **AC-5 — a loopback-only listener is invisible to the collision probe on Windows.** `env_preflight._port_busy` binds `0.0.0.0:<port>` with no socket options; Windows lets that succeed beside a socket bound to `127.0.0.1:<port>`, so the probe reports "free". A natively installed Postgres listens on `localhost` by default — the ambient-Postgres collision L21 describes. Reproduced on the real host (dogfood item 2: listener on `0.0.0.0:55432` → `port-collision`; listener on `127.0.0.1:55432` → no finding). Verified on this host that setting `SO_EXCLUSIVEADDRUSE` on the probe socket before the wildcard bind makes both cases report busy; probing `127.0.0.1` in addition to `0.0.0.0` also works. Either satisfies `test_real_bind_probe_detects_a_loopback_only_listener` (`template/tests/unit/scripts/test_env_preflight.py`). Keep the "socket closed immediately, no state survives" property.

2. **AC-5 — a bare short-form entry is probed as a host port.** `_SHORT_PORT_RE` / `_extract_host_token` treat `"3000"` (or `3001`) as host port 3000. In the Compose short syntax `[HOST:]CONTAINER[/PROTOCOL]` a bare value is the *container* port and the host port is ephemeral, so there is no host port to check; probing 3000 is a guessed port, which the FR's Open-question default forbids, and yields a false `port-collision` warn (and a `preflight=port-collision` metrics segment) whenever anything listens on that number. The comment on `_SHORT_PORT_RE` states the opposite of the spec. Satisfy `test_bare_container_port_publishes_no_known_host_port_and_is_not_probed` (fixture `template/tests/fixtures/env-preflight/compose/bare-container-port.yml`): a short-form entry with no `:CONTAINER` part publishes no known host port and is skipped.

3. **Open-question default (AC-5 ports) — unresolved `${VAR}` ports are not surfaced on a clean run.** `_run_env_preflight` returns at the `PREFLIGHT OK` early exit before the `PREFLIGHT NOTE unresolved ports:` line, so an operator whose only compose port is `"${DB_PORT}:5432"` with `DB_PORT` unset reads `PREFLIGHT OK ran: docker, ports` and never learns the port was not checked. The FR's default says the skipped port is "include[d] in the `PREFLIGHT OK`/`WARN` line's list"; the PR body claims this is done. Satisfy `test_unresolved_ports_are_surfaced_on_a_clean_run_too` (`test_dispatch_env_preflight.py`): print the unresolved list (the NOTE line, or appended to the OK line) whether or not there are findings.

4. **AC-6 / AC-10 — `PREFLIGHT OK (no stack declared)` is printed for a declared stack.** The label is chosen from `result.checks_ran` being empty, not from the detected stack being empty. A `pip`-only project on Linux/macOS (no docker, no PATH tool, no Windows check) — and any harness that stubs the AC-9 seam with `PreflightResult()` — declares a stack and gets a line asserting it does not. AC-10 reserves that wording for `detect_stack == []`; AC-6 says the OK line "names the checks that ran". Satisfy `test_ok_line_on_a_declared_stack_never_claims_no_stack_declared`: branch on the tool list (`tools` empty → AC-10's line; otherwise `PREFLIGHT OK ran: …`, with an explicit "(none)" when nothing ran).

Not kicked back, noted under FINDINGS: AC-3 remedy provenance, the IP-prefixed / range / `.env` compose spellings, AC-9's `_dispatch/` clause vs the pre-existing dry-run synthesis file, AC-8's wave record shape, the metrics README drift.
