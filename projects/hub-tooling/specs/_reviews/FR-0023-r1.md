## Kick-back items

### B-1 (blocking, AC-1): `project_name` accepts a trailing newline

`project_layout._project_name` validates with `_PROJECT_NAME_PATTERN.match(value)`, where the pattern is `^[a-z0-9][a-z0-9-]*$`. In Python, `$` also matches just before a final `\n`. So `"demo\n"` loads as a valid `project_name`. YAML produces that value from any of these:
- `project_name: "demo\n"`;
- the literal block `project_name: |` followed by `demo`;
- the folded block `project_name: >` followed by `demo`.

The gate then builds `#\s*covers\s+demo\n\s+(FR-…)` from it. Every ordinary `# covers demo FR-NNNN:AC-N` stops counting, and the layout still reports as valid. The project sees `coverage-missing` failures with no pointer to the cause.

AC-1 requires `project_name` to match `^[a-z0-9][a-z0-9-]*$` (lowercase letters, digits and `-`, as `layout.yaml.example` says), and a malformed value to raise. A value holding a newline is not such a name.

- **Fix:** in `template/scripts/project_layout.py`, change `_PROJECT_NAME_PATTERN.match(value)` to `_PROJECT_NAME_PATTERN.fullmatch(value)`. Keep the pattern text, so the error message is unchanged.
- **Optional:** add `("name-trailing-newline", 'project_name: "demo\\n"\n', "project_name")` to `_MALFORMED` in your own test file.
- **Done when:** `test_project_layout_adversarial.py::test_project_name_with_a_trailing_newline_is_malformed` passes. It fails now in all three parameters, `DID NOT RAISE`.

`footprint_root` is not affected: it is compared by string equality, and my `root-newline` case confirms it.

No other blocking item. The non-blocking findings and the escalation are below.

## ESCALATION

**FR-0023:AC-1 / AC-3: Windows drive-letter entries pass "no absolute path".**
- **The gap.** AC-1 checks `gate.*_dirs` with "the same rules as `owns:` entries (`spec_footprint._validate_glob`: no absolute path, …)". `_validate_glob` rejects only a leading `/`. On Windows, `C:/x` is absolute, and `root / "C:/x"` discards the root.
- **Reproduced in the dogfood throwaway** with `gate: {source_dirs: ["<%TEMP%>/df23x"]}` (a `C:/…` path):
  - `index-specs.py --validate` passes;
  - `deploy-gate.py` crashes with `ValueError: '…\df23x\m.py' is not in the subpath of '…\df23'` from `relative_to`;
  - that is `script-error`, with a traceback.

  AC-3 says a directory outside the project "no longer raises `ValueError` from `relative_to`".
- **Why the Developer cannot fix it alone.** `solution_space.fixed` line 2 keeps `owns:` syntax unchanged, so `_validate_glob` cannot change. Adding a check in `project_layout.py` alone would make the layout rules stricter than "the same rules as `owns:`".
- **Proposed default.** `project_layout._dir_list` also rejects an entry with a Windows drive or UNC root (`PureWindowsPath(v).drive` non-empty), with the usual `LayoutInvalid` naming `gate.<key>`. `owns:` is unchanged. The risk is low, because the file is human-authored under the protected `.agent-team/`. The failure is loud, not silent. This does not block B-1's round.
