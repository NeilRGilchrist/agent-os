## FINDINGS

1. [minor] **Deterministic synthesis failure re-raises out of the handler.** Pinned by `test_a_deterministic_synthesis_failure_still_prints_crashed_but_reraises`: when `_write_wave_synthesis` raises every time (e.g. `OSError` on `_dispatch/`), the handler prints `CRASHED — Synthesis: OSError: disk full` + traceback (flushed) and then its own synthesis call raises again, so `cmd_wave` exits via the unhandled exception (process exit 1, no file, no record) rather than returning `3`. The Developer flagged this in `PR_BODY.md`; I agree it is a finding, not a kick-back: the CRASHED line and stdout traceback survive (the visibility AC-3 exists for), and AC-4's "synthesis still written" is impossible by construction when the writer itself is broken. A follow-up could wrap the handler's `_write_wave_synthesis` call in its own `try/except` that prints a second `CRASHED — Synthesis (during crash handling)` line and still returns `3`.
2. [minor] **A crash after a successful synthesis records the wave twice.** Pinned by `test_a_crash_after_synthesis_in_park_findings_emits_a_second_wave_record`: with `--park-findings`, a raise inside `_park_findings` (after `_write_wave_synthesis` has already emitted the record) is caught with `current_phase == "synthesis"` and the handler synthesises again — same file path (overwritten), but a second identical `dispatch.wave` record. Exit `3` and the CRASHED line are correct. Not an enumerated AC-3 site (`_park_findings` is opt-in and post-synthesis), so a finding: a `synthesis_written` flag (or `current_phase = "park-findings"` with the re-write skipped) would close it in two lines.
3. [spec] **A rework-round crash leaves no trace in the record or synthesis.** Pinned by `test_a_rework_round_crash_leaves_the_round1_completed_fr_unmarked`: per AC-4's terminal-state rule (and the FR Notes: "`completed_e2e` FRs … are not re-marked"), an FR whose round 1 finalized both legs is `completed_e2e`, so a crash in its round 2 is not marked — the record shows `completed == 1`, `dropped == 0`, `drop_reasons == []`, `rounds_ran == 1`; only the `CRASHED — rework:` line and exit `3` carry the crash. The implementation follows the AC literally; for the Architect: consider whether a crash inside a rework round should surface in the record (e.g. a `rework-round-N-crash` entry, which `_run_rework_rounds` already has the slug vocabulary for) so the metrics do not read as a clean completion.
4. [info] **A stdout whose `flush()` raises is surfaced, not hidden.** Pinned by `test_a_stdout_whose_flush_raises_surfaces_the_error_rather_than_hanging`: a `BrokenPipeError` from the first flush propagates from Phase 0 (outside the handler); from the second flush onward it is caught, the `CRASHED — Phase 1: Dev Tick: BrokenPipeError` line is written, and the handler's own `flush=True` re-raises it, so the process still dies by `BrokenPipeError` with no record. Pre-FR the same dead consumer surfaced only at exit or buffer-fill; the wave never hangs or spawns. No action needed for the Orchestrator's redirect-to-file use.

[nit] Three per-FR lines in the wave body are not `flush=True`: the `FORCE-ESCALATE` line in `_run_rework_rounds`, `_wait_for_phase`'s `TIMEOUT — killed pid=` line, and the `--- Dry-run: remaining phases …` banner (`PR_BODY.md` lists "the dry-run banner" among the flushed sites; it is not, though the flushed `WOULD-RUN` line that follows it pushes it through immediately). Each is followed within milliseconds by a flushed line or process exit, so AC-5's observable holds; listed for completeness.
