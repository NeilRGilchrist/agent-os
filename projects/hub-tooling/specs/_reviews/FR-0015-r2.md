## K2-shape ruling (second `git diff --no-renames` call, unioned)

**I accept the union. It is not a kick-back.**
- **Correctness.** `--no-renames` output is a superset of the renames-default output: a rename prints both the old and new names, and a copy prints the new name. So the union equals the `--no-renames` set and cannot narrow anything.
- **Failing closed.** A failure of *either* call is a refusal. It quotes the first non-empty line. This is now pinned for the second call on its own, and for both dry-run staged reads.
- **Cost.** One extra `git diff --name-only` on the AC-2 range, plus one more staged read in dry-run only. That is negligible next to finalize's push and `gh` calls.
- **Clean-run identity.** `_git_capture` captures output and prints nothing. `test_k2_clean_run_makes_both_range_reads_and_prints_nothing_extra` shows exactly two range reads and no extra line. Byte identity against `82670a5` holds: `test_clean_finalize_is_byte_identical_to_the_base`, 4 roles × hand-made or spawned, is green.

My round-1 test **did** pin an implementation detail. `_is_range_diff` required the exact three-element argv, which forced the maintainer to keep a now-redundant call. I loosened it to match any `git diff` over the `<base>...<branch>` range, whatever its flags. That is the only edit to a pre-existing test: the helper `_is_range_diff`, used by `test_a_diff_that_cannot_run_is_a_refusal_quoting_the_first_line`. That test stays green, and it now fails the first range read whichever form it takes.

I do **not** require a single `--no-renames` call. Collapsing the two into one is now permitted, since no test blocks it, but it is optional.

## FINDINGS

Carried forward from round 1 (Architect-bound, still open; round 2 did not touch them):
- **Re-running finalize after `--revalidate` falsely refuses (AC-2 spec gap).**
  - After AC-7 merges an upstream change to a protected path, and while local `main` is behind `origin/main`, the next `finalize --role dev` blames the branch for upstream work.
  - The fix is a spec choice: diff against the merge-base with `origin/main`, or exclude merge-brought paths.
  - `mnt`'s footprint check has the same class of problem on its first `--revalidate` run. That is pre-existing FR-0013 behaviour.
- **Committed off-limits paths under a broad `mnt` `owns:` glob pass (spec gap; K1's committed-side twin).**
  - `mnt_footprint_violations` is frozen by DEC-0017 Decision 4 and uses plain `fnmatch` against `owns:`. So a committed `CLAUDE.md` under `*.md`, or `scripts/deploy-gate.py` under `scripts/*`, reaches a PR.
  - Round 2's K1 predicate covers only the uncommitted side.
  - This needs an AC or DEC, perhaps alongside IDEA-0088.
- **The AC-1 `NOTE` also prints when no Reviewer was involved.** It fires for any protected violation, including the maintainer's own commit. The refusal is correct, but the wording misleads.
- **Stale AC-4 records.**
  - `_record_settings_digest` silently keeps the previous record when read-back fails.
  - Records are never removed when `reconcile` removes a worktree, so a hand-recreated worktree inherits a stale record and refuses.
- **Pre-existing, out of scope.** `spec_footprint._validate_glob` accepts a Windows-absolute `owns:` entry such as `C:/x` (FR-0009).
- **Harness and `uv run python -c`.** Not blocked, as recorded in round 1. This confirms DEC-0014's code-reading assertion live.
- **Resolved by round 2:** AC-2's dry-run staged read no longer goes through fail-open `_staged_paths`. It is now fail-closed, and tested.

New in round 2:
- **Non-ASCII path names evade AC-2 and AC-3 (Architect, new).**
  - git's default `core.quotePath=true` prints a path like `.agent-team/hooks/évil.py` as `".agent-team/hooks/\303\251vil.py"`, in quotes and octal-escaped. That string does not match `.agent-team/**` under `fnmatch`.
  - A *new* non-ASCII-named file under `.agent-team/`, whether committed (AC-2) or untracked (AC-3), is therefore not refused. I verified this live with `ls-files --others`, default `diff` and `--no-renames`.
  - Existing protected files have ASCII names, and renaming one away still reports its old name, so the practical exposure is new files only. That is why this is a finding and not a kick-back.
  - The fix would be `-c core.quotePath=false` or `-z` on the AC-2/AC-3 reads. AC-3 says those reads use "the same git commands FR-0006 AC-3's helpers run", so whether that flag is allowed is the Architect's call.
- **`fnmatch` versus harness glob semantics under `mnt` (FR-0009, pre-existing).**
  - `_owned` uses `fnmatch`, where `*` crosses `/`. So `owns: [".agent-team/*"]` counts `.agent-team/roles/reviewer.md` as owned, and `mnt_permission_rules` emits no sibling denies.
  - The harness's `Edit(.agent-team/*)` does not match nested paths. AC-3 therefore treats an interpreter write there as not off-limits, even though no rule actually granted it.
  - This is consistent with FR-0015's Term, which specifies the `fnmatch` rule, but it is a gap for the IDEA-0088 / FR-0009 follow-up.
- **The AC-4 error wording for a corrupt record.** A corrupt record is reported as "permission file changed since it was written: <record> is not valid JSON". It refuses correctly, but the prefix blames the permission file when the record is what failed. This is cosmetic and optional to fix in round 3.
