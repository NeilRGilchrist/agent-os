## Kick-back items

**K1 (AC-3, FR-0015 "Term used below"): a broad `owns:` glob makes a denied control-plane path "granted".**
- **What is wrong:** `_off_limits_worktree_paths` (dispatch.py:4198-4210) returns `[p for p in protected if not _owned(p, granted)]`. With `owns: ["src/**", "*.md"]`, `CLAUDE.md` matches `*.md`, so it is not off-limits. The Term says MNT_NEVER_WRITABLE "is always off-limits", and `mnt_permission_rules` still denies `CLAUDE.md`. The same happens for `scripts/*` with `scripts/deploy-gate.py` (still denied, because `_protected_touched` requires the exact entry) and for `**` with `.agent-team/**` (still denied). In each case the harness forbids the write and AC-3 then waves an interpreter write through. The docstring's claim that `MNT_NEVER_WRITABLE` "stays off-limits for `mnt` even when owned" holds only for the literal entry.
- **What would satisfy me:** for `mnt`, a protected path is off-limits unless the derivation actually grants it: `p in MNT_NEVER_WRITABLE or not _owned(p, granted) or _owned(p, denies)`, with `denies` taken from the same `mnt_permission_rules` call. Tests: the three `test_mnt_broad_owns_glob_…` go green, and `test_mnt_unstaged_change_to_an_owned_protected_path_is_only_warned` stays green.

**K2 (AC-2): rename detection hides a protected path that left the branch.**
- **What is wrong:** `git diff --name-only <base>...<branch>` detects renames by default and prints only the new name. So `git mv scripts/deploy-gate.py src/gate.py`, committed, produces `src/gate.py` only, and finalize pushes and opens the PR. The same applies to a staged rename in dry-run (`_staged_paths` uses `diff --cached --name-only`).
- **What would satisfy me:**
  - Pass `--no-renames` to AC-2's range diff.
  - For the dry-run staged set, use an AC-2-private read with `--no-renames`. Do not change `_staged_paths`, because FR-0006's `WOULD-COMMIT` count depends on it.
  - Ideally that read fails closed too; today it goes through fail-open `_staged_paths`.
  - Tests: `test_renaming_a_protected_file_away_is_a_control_plane_change[dev,rev,bkf]` and `test_dry_run_staged_rename_of_a_protected_file_is_counted` go green.

**K3 (AC-4, fixed rule "a check that cannot run is a refusal"): an existing but unreadable record is a silent pass or a crash.**
- **What is wrong:** `_finalize_settings_digest_violation` (dispatch.py:2178-2210) returns `None` on `OSError` or `JSONDecodeError` and on missing `path`/`sha256`, and raises `AttributeError` on a non-object record.
- **What would satisfy me:**
  - A record that exists but cannot be read, is not a JSON object, or lacks either key produces one `ERROR` (or `WOULD-REFUSE`) line naming the record and the cause, with the same exits as AC-4. It must never raise.
  - "No record" (file absent) stays silent.
  - Tests: `test_a_record_that_exists_but_cannot_be_read_is_a_refusal[4 shapes]` go green.

Everything else is approved as is. None of the three fixes touches a frozen name, how the permission file is written, or clean-run output.

## FINDINGS

- **Harness and `uv run python -c` (asked by FR-0015 Notes).** It was **not** blocked. My own session ran it unprompted. The `mnt` permission file it runs under allows `Bash(uv *)` and `Bash(docker *)` and denies only the prefixes `Bash(python -c*)`, `Bash(python3 -c*)` and `Bash(py -c*)`, which `uv run python -c` does not match. `docker run -v` also wrote through the bind mount. This confirms DEC-0014's code-reading assertion live.
- **Re-running finalize after `--revalidate` falsely refuses (AC-2 spec gap, for the Architect).** After AC-7 merges an upstream (`--upgrade`) change to a protected path into a dev branch, and while local `main` is behind `origin/main`, the *next* `finalize --role dev` reports `claude/dev-FR-0004 touches control-plane path(s)…: scripts/deploy-gate.py`, blaming the branch for upstream work. This was reproduced live in the dogfood; finalize is documented as idempotent. The first run is correct, as the placement note intends. The fix is a spec choice: diff against the merge-base with `origin/main`, or exclude paths the merge brought in. `mnt`'s footprint check has the same class of problem even on the *first* `--revalidate` run, because it runs after the merge; that is pre-existing FR-0013 behaviour.
- **Committed off-limits paths under a broad `mnt` `owns:` glob pass (spec gap, for the Architect).** FR-0015's What says finalize refuses a committed off-limits path "whoever committed it", but for `mnt` the only committed-path check is `mnt_footprint_violations`. It uses plain `fnmatch` against `owns:`, and DEC-0017 Decision 4 freezes it. A committed `CLAUDE.md` under `owns: ["*.md"]`, or `scripts/deploy-gate.py` under `scripts/*`, reaches a PR. This is K1's twin on the committed side. It needs an AC or DEC, perhaps alongside IDEA-0088.
- **The AC-1 `NOTE` also prints when no Reviewer was involved.** It fires for any protected violation, including the maintainer's own commit (seen live on FR-0001). There it says "Reviewer provenance never exempts…" about a path the Reviewer never touched. The refusal is still correct; only the wording misleads. Suggested fix: print it only when AC-5(a) would otherwise have exempted the path, or reword it.
- **Stale AC-4 records.** `_record_settings_digest` silently does nothing when the read-back fails, which leaves the *previous* record in place. Records are also never removed when `reconcile` removes a worktree, so a hand-recreated worktree at the same path inherits a stale record and refuses. That contradicts "no record means skip" for by-hand worktrees. Low priority.
- **AC-2's dry-run staged read uses fail-open `_staged_paths`.** A failed read silently shrinks the dry-run set. This is dry-run only; it is mentioned in K2's remedy.
- **Defence in depth, observed.** In the normal flow, AC-2 now refuses the Reviewer's finalize before FR-0013's AC-1 fast-forward. AC-1's scenario is therefore reachable only through a hand or pre-FR-0015 fast-forward, as in the dogfood.
- **Pre-existing, out of scope.** `spec_footprint._validate_glob` rejects only a leading `/`, so a Windows-absolute `owns:` entry such as `C:/x` passes AC-5 for every role (FR-0009).
- Every `file:line` in the maintainer's PR_BODY was checked and is accurate, within a line or two for comment offsets.
